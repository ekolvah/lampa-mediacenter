## Context

Мотивация описана в proposal.md. Ядро Lampa строит рекомендации само: держит очередь
`recomends_scan`, по каждой её записи берёт TMDB `/recommendations` и пишет `recomends_list`.
Плагин не заменяет ни сканирование, ни ряд. Он только подкладывает ядру KP-историю в понятной ядру
форме и чистит список.

## Standard approach

**Код ядра на приставке.** Наблюдение: `http://lampa.mx/app.min.js?v=1994617`, исходники функций
сняты через `tools/cdp.py` 2026-11-20 (`String(Lampa.Recomends.init)` и `fetch` бандла в WebView).
Модуль совпадает с `yumata/lampa-source` `src/core/recomend.js`
(https://github.com/yumata/lampa-source/blob/main/src/core/recomend.js).

- `init`: `data = Storage.cache('recomends_scan', 300, []); Timer.add(120 * 1000, function () { … })`.
  В теле таймера в `data` добавляются записи истории `if (['cub', 'tmdb'].indexOf(elem.source) >= 0)`
  в виде `{id: elem.id, tv: elem.number_of_seasons || elem.seasons}`, если записи с таким `id` ещё нет.
  Потом `Storage.set('recomends_scan', data); search();`.
- `search()`: `var ids = data.filter(e => !e.scan)`, берётся `ids[0]`, у неё ставится `scan = 1` и
  вызывается `TMDB.get((elem.tv ? 'tv' : 'movie') + '/' + elem.id + '/recommendations', …)`.
  Из записи используются только `id` и `tv`, в историю функция не ходит. В
  `Storage.cache('recomends_list', 100, [])` попадают тайтлы, которых там ещё нет, чьего `id` нет в
  истории (`h.id == e.id`) и чей год больше текущего минус 20. Когда непросканированных нет, у всех
  записей сбрасывается `scan = 0`. В конце вызывается `Storage.set('recomends_scan', data)`.
- Ряд: `ContentRows.add({name: 'recomend_watch', screen: ['main', 'category'], call: …})` берёт
  внутренний `get$4(media)`. Тот отбирает записи по типу
  (`e.number_of_seasons || e.first_air_date` — сериал) и убирает те, что есть в истории
  (`!history.find(h => h.id == e.id)`), затем показывает 20 случайных.
- **`Timer.add` периодический.** `Lampa.Timer.init`: `setInterval(…, 1000)`, и для каждого таймера
  `if (now - t.last >= t.interval) { t.last = now; t.call(); }`, на паузе при скрытом окне. Значит,
  ядро каждые 120 с, пока окно видно, сканирует одну запись и перезаписывает `recomends_scan` своим
  `data`.
- Порядок старта (`startApp` в том же бандле): `Plugins.init(); … Recomends.init(); … window.appready
  = true; Lampa.Listener.send('app', {type: 'ready'})`. На событии `ready` у ядра уже есть `data`.
- **`data` ядра и `Lampa.Storage.get('recomends_scan')` — один объект.** Проба 2026-11-20 на приставке
  (`snapshots/2026-11-20_recomends-scan-probe/NOTES.md`): в `Lampa.Storage.get('recomends_scan')[0]`
  на месте, без `Storage.set`, добавлено поле `probe: 1`. Через ~50 с, на тике ядра (непросканированных
  стало 22→21), `localStorage.getItem('recomends_scan').indexOf('probe')` дал `25`, а до тика давал
  `-1`. Кроме того, `Lampa.Storage.get('recomends_scan') === Lampa.Storage.get('recomends_scan')` →
  `true`.
- `search()` берёт `Storage.cache('recomends_list', 100, [])` заново на каждом тике, дописывает новое
  в конец (`recomend.push(e)`) и зовёт `Storage.set('recomends_list', recomend)` (бандл ядра выше,
  скачан с ПК 2026-11-20). Ключи `recomends_scan`/`recomends_list` встречаются в бандле только в этом
  модуле и в списке ключей «очистить кэш». Строка `settings_cub_sync_recomends` есть только в словарях,
  кодом не используется. Модуль `sync` Lampac (`docs/lampa-config-review.md`, строка `on.js`) не
  проверен: он грузится по URL с токеном аккаунта.
- Запрос движка (`Lampa.Reguest`, тот же бандл): вызов, снятый `clear()`, колбэков не получает
  (`if (_calls.indexOf(call) !== -1 && call.error) call.error(data)`). Поэтому ответ на запрос может не
  прийти вообще.
- **Запись ядра видна через `Lampa.Storage.listener`.** `Storage.set(name, value, nolisten)` шлёт
  `listener.send('change', {name, value})`, если не передан `nolisten` (исходник `Lampa.Storage.set` на
  приставке). Проба 2026-11-20: подписка `Lampa.Storage.listener.follow('change', …)` на одном тике ядра
  получила `recomends_scan` ×2 и `recomends_list` ×2 (интервал в ~190 мс).

**Данные истории на приставке (там же, 2026-11-20).** 61 запись: 37 `KP`, 20 `tmdb`, 4 `cub`. У
KP-записей нет поля `type`. Тип виден по `number_of_seasons` / `first_air_date` (15 сериалов). У 27 из
37 есть `imdb_id`, `tmdb_id` нет ни у одной. Пример записи без `imdb_id`: `KP_5146946`, «Операция
«Возмездие»», `original_title` «The Fix», `release_date` `2026-09-11`. Пример с `imdb_id` и найденным
TMDB-тайтлом — тот же разбор у трейлеров (spec `kp-card-trailers`, «По imdb_id и фильм, и сериал»).

**Готовые решения.** Не нашлись (поиск описан в issue #77): GitHub code search по `recomends_scan`,
`recomends_list`, `Lampa.Recomends`, плюс веб-поиск. `nb557/kp_source.js` только читает
`Lampa.Recomends.get()`. `smart_recommend.js` (BazZziliuS) делает отдельный пункт меню и шлёт
`KP_…` id прямо в TMDB.

## Goals / Non-Goals

**Goals:** ядро сканирует KP-историю так же, как свою, и уже просмотренное через KP не всплывает в
ряду.

**Non-Goals:**
- Своё сканирование `/recommendations` и свой ряд. Решено пользователем: темп ядра.
- Правка истории (`Favorite`). Ядро читает из неё `source`, `id` и тип, но запись с TMDB id вместо
  `KP_<n>` или рядом с ней видна в разделе «История». Подробнее — в
  «Отвергнуто» решения 2.
- Записи `recomends_scan`, которые не нашлись в истории (4 на приставке). Это поведение ядра.

## Decisions

### 1. В `kp-reactions-fix.js`, а не отдельным плагином

Поиск TMDB-тайтла по KP-записи с запасным поиском по названию и году уже есть в
`kp-reactions-fix.js` (`resolveTitle`, spec `kp-card-trailers`, с тестами). Отдельный плагин
скопировал бы этот поиск, и правила сверки названий разошлись бы. Плагин уже подключён на приставке и
держит KP-мосты к TMDB (трейлеры, реакции, ряды новинок). Цена — ещё одна зона ответственности в
одном файле.

`resolveTitle` живёт в замыкании `patch()`, которое запускается, когда загрузился источник KP. Поэтому
новый код вызывается из `patch()` и ждёт готовности приложения (`window.appready` или
`Listener` `app` `ready`). Второго пути старта нет. У записи истории нет `type`, а `resolveTitle` и
`releaseDate` берут тип из `movie.type`. Поэтому в них передаётся копия записи с `type: 'tv'`, если у
записи есть `number_of_seasons` или `first_air_date`, иначе с `type: 'movie'`.

### 2. Вставка в общий массив очереди

KP-записи ищутся по одной, в порядке истории: следующий `resolveTitle` — из колбэка предыдущего. Так
поиск не идёт залпом одновременно с рядами Главной KP, которые в первом сеансе дня сами шлют ~50
запросов (риск R12 в архивном `2026-11-18-now-watching-new-releases/design.md`). Торопиться некуда: ядро берёт одну запись очереди
раз в 120 с. Ответ может не прийти совсем (Standard approach, `Lampa.Reguest`), поэтому на весь проход
есть общий предел `RECS_TIMEOUT_MS = 60000`, меньше первого тика ядра. Предел держит существующий
`waiter()`, которому таймаут передаётся параметром (сейчас он зашит как `ROWS_TIMEOUT_MS`). Записи, до
которых проход не дошёл к пределу, считаются пропущенными (решение 4). В следующем запуске ответы уже
найденных записей берутся из кэша движка (`life: WEEK`), и проход доходит дальше.
Когда проход закончен или вышел предел, плагин берёт массив `Lampa.Storage.get('recomends_scan', '[]')`, вставляет в его
начало недостающие `{id, tv: true|false}` (`unshift`, в порядке истории — свежие первыми) и зовёт
`Lampa.Storage.set` с тем же массивом. Правка на месте нужна потому, что это тот же объект, который
ядро перезаписывает на каждом тике (Standard approach, проба). Дубликат определяется по `id` и
истинности признака сериала: у ядра это число сезонов, а `search()` проверяет только истинность.

Отвергнуто:
- «Свой массив + `Storage.set`» или «писать после первого тика». Ядро перезаписывает ключ своим
  массивом каждые 120 с, и чужой массив пропадёт на следующем тике.
- «Все запросы сразу под `ROWS_TIMEOUT_MS`». Это залп поверх рядов Главной, а 5 с — бюджет экрана,
  которого здесь нет.
- «Записывать TMDB id в саму историю». Это могло бы быть при открытии карточки в `KP.full`, плюс
  разовая дозапись старых записей. Тогда ядро само взяло бы такие записи в очередь и в фильтр. Но
  запись в истории с другим `id`/`source` — это дубль в «Истории» и правка пользовательских данных.
  Разовая дозапись всё равно требует того же поиска. Поиск по кэшу
  движка при каждом запуске дешевле, чем такая миграция.
- «Своя карта `kp_id → tmdb` в Storage». Это лишний ключ, который надо поддерживать и
  инвалидировать, а кэш `find`/`search` движка уже даёт то же.

### 3. Чистка `recomends_list`

Фильтр ядра по истории сравнивает `KP_<n>` с числовым id и просмотренное через KP не отсекает. После
поиска плагин строит `Set` строк `<id>:<tv|movie>` из найденных тайтлов. Одна функция чистки убирает
из массива `Lampa.Storage.get('recomends_list', '[]')` на месте (`splice`) записи, чьи `id` и тип
(`number_of_seasons || first_air_date`) есть в `Set`. Слушатель держит только этот `Set`, без записей
истории. Чистка вызывается:
- после поиска: если что-то убрано, `Storage.set` сохраняет список на диск, иначе записи нет;
- на каждом `Lampa.Storage.listener` `change` с `e.name === 'recomends_list'`, то есть после записи ядра
  на тике. Здесь только `splice`, без `Storage.set`. Ряд читает тот же объект в памяти, а на диск
  чистый список попадает со следующей записью ядра или с чисткой следующего запуска. Так нет лишней
  записи на 100 элементов на каждом тике, и нет повторного события
  `change` от плагина.

Отвергнуто: обернуть `Lampa.Recomends.get`. Ряд зовёт внутренний `get$4` по замыканию, и обёртка его
не затронет (Standard approach).

### 4. Пропуски видны одной строкой

`resolveTitle` уже пишет причину по каждой записи (`no title match …`, `find failed …`). Плагин
добавляет итог: `console.warn('kp-reactions-fix: recommendations: <пропущено> of <всего> KP history
titles unresolved')`, если пропущено больше нуля. Пропущенные — ненайденные, с ошибкой поиска и те,
до которых проход не дошёл к `RECS_TIMEOUT_MS`. Очередь и список обновляются по найденным.

### 5. Подмену очереди видно

Вставка держится, только пока ядро пишет тот же массив (решение 2). Новая версия ядра с
`lampa.mx` или модуль `sync` Lampac могут заменить массив, и тогда вставки тихо пропадут на
ближайшем тике. Живая проверка это ловит только при смене пина плагина, а ядро обновляется само.
Поэтому на первом `change` с `e.name === 'recomends_scan'` после вставки плагин проверяет, что
вставленные id есть в `e.value`. Если нет, он пишет `console.warn('kp-reactions-fix: recommendations:
core rewrote recomends_scan without KP history titles')`. Проверка одна за запуск: дальше событие
не слушается. Собственный `Storage.set` плагина при вставке тоже шлёт `change`, поэтому подписка
делается после него.

## Risks / Trade-offs

- [Новая версия Lampa или модуль `sync` Lampac перестанут делить объект `recomends_scan` с
  `Storage.get`] → вставки живут до ближайшего тика. Это видно в консоли (решение 5) на каждом
  запуске, а при обновлении плагина — по живой проверке (задача 5.2). Чистка списка в памяти от этого
  не зависит: она идёт на каждом `change`.
- [Ядро хранит в очереди до 300 записей и при переполнении режет с начала, то есть наши] → записи
  истории ограничены 100, поэтому до среза далеко. Если он случится, следующий запуск вставит
  недостающие снова: вставка идемпотентна.
- [Поиск по названию без года берёт только единственное совпадение] → часть KP-записей пропускается
  с предупреждением. Ложное совпадение хуже пропуска (правило уже принято в `kp-card-trailers`).
- [Синхронизирует ли модуль `sync` Lampac эти ключи, не проверено (Standard approach)] → если да,
  вставки и чистка дойдут до других устройств аккаунта, и это желаемо. Если он подменяет массив,
  это ловит решение 5. Откат из снапшота может перебить синхронизация, но откат и не нужен
  (Migration Plan).
- [Раз в неделю, когда кэш движка истекает, проход заново делает до ~37 запросов по одному] → это
  до минуты фоновой работы после старта. Не дошедшие к пределу записи видны в предупреждении.

## Migration Plan

После merge `main` пин `kp-reactions-fix.js` на приставке переводится на новый sha, со снапшотом по
`docs/snapshots-convention.md`. Откат — вернуть прежний sha. Записи, уже вставленные в
`recomends_scan`, ядро просто дальше сканирует. Удалять их не нужно, но можно восстановить ключ из
`before/` снапшота.
