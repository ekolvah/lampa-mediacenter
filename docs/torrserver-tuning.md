# TorrServer: текущая настройка и как её менять

`ru.yourok.torrserve` (сборка MatriX) — локальный торрент-клиент, которому  
Lampa передаёт magnet через Android Intent. Свой HTTP/API на `:8090` активен,  
только пока идёт воспроизведение (движок ленивый, поднимается по запросу).  
Настройки хранятся на диске в BBolt-файле  
`/storage/emulated/0/Android/data/ru.yourok.torrserve/files/config.db`, под  
ключом `BitTorr…`, и читаются оттуда при каждом старте движка.

## Текущее состояние (2026-08-30)

| Параметр | Значение | Зачем |
| --- | --- | --- |
| `ConnectionsLimit` | **100** | было 25 — упор подтверждён логом: активных пиров ровно 25 независимо от размера роя. |
| `CacheSize` | **209715200** (200 МБ) | было 64 МБ — на 4K ~30 Мбит/с это ~53 с запаса вместо ~17 с. |
| `PreloadCache` | **16** (%) | скорректирован вместе с `CacheSize`, чтобы преднагрузка осталась ~32 МБ, а не выросла втрое (иначе старт воспроизведения удлиняется). |
| `ReaderReadAHead` | **95** (%) | доля кэша под буфер ВПЕРЕДИ позиции чтения (остальное держится позади, под перемотки назад). Дефолт апстрима, историческое значение на этом устройстве. При 200 МБ кэша и битрейте 4K-серии ~12 Мбит/с это ~2 мин запаса. Самое хрупкое поле: минимум, до которого TorrServer клампит обнулённое значение, — **5**, то есть ~7 с буфера, и воспроизведение начинает видимо прерываться. |
| `PeersListenPort` | **42100** | было `0` (случайный порт при каждом рестарте) — нужен фиксированный порт, чтобы проброс (UPnP или ручной) вообще имел смысл дольше одного сеанса. |
| `RetrackersMode` | **1** | было `0` («не добавлять») — не дефолт апстрима TorrServer (там `1`). При `0` раздача видела только трекеры из своей magnet-ссылки, без встроенного списка публичных ретрекеров TorrServer. Для малосидовых раздач это меньше путей найти пира через трекер независимо от DHT/PEX. |
| `DisableUPNP`/`DisableDHT`/`DisablePEX` | все `false` | дефолты MatriX, менять не нужно — уже включено. |

## Как менять настройку — обязательный метод

API TorrServer: `POST http://127.0.0.1:8090/settings`, тело  
`{"action":"get"}` или `{"action":"set","sets":{...}}`. С хоста — через  
`adb forward tcp:18090 tcp:8090` и `curl http://127.0.0.1:18090/settings`.

`**action:"set"**` **не мёржит присланный объект с текущими настройками — он**  
**заменяет структуру целиком.** Любое поле, не указанное в `sets`, обнуляется  
до нулевого значения Go (`int`→0, `string`→`""`), а не остаётся прежним. Это  
подтверждено дважды экспериментально на живом устройстве 2026-08-30: частичный  
вызов с двумя полями (`CacheSize`, `PreloadCache`) мгновенно откатил  
`ConnectionsLimit` со 100 на 25, обнулил `TMDBSettings.APIURL/ImageURL/ImageURLRu`  
(непустые строки-дефолты) до `""` и сбил `ReaderReadAHead` с 95 до минимума 5  
(0 → кламп) — без единого сообщения об ошибке. Это же,  
судя по характерной подписи (сброшенный `PreloadCache` был **0** — нулевое  
значение Go, а не старый дефолт **50**), — вероятная причина, по которой правка  
от 22 августа 2026 бесследно исчезла при следующем перезапуске процесса:  
кто-то (или что-то) применил частичный `set` вместо полного объекта.

Официальный веб-интерфейс TorrServer (`main.*.chunk.js`, вкладка настроек)  
обходит эту опасность так: сначала `{"action":"get"}` → берёт объект целиком →  
точечно мутирует нужные поля на клиенте → отправляет **тот же полный объект**  
обратно через `{"action":"set","sets":{...}}`. Делать вручную — так же:

```
MSYS_NO_PATHCONV=1 adb -s <ip>:5555 forward tcp:18090 tcp:8090

# 1. Взять текущий объект целиком
curl -s -X POST http://127.0.0.1:18090/settings -H "Content-Type: application/json" \
  -d '{"action":"get"}'

# 2. Скопировать весь JSON из ответа, поправить в нём только нужные поля,
#    отправить обратно ЦЕЛИКОМ (не собирать sets с нуля, не слать частичный объект)
curl -s -X POST http://127.0.0.1:18090/settings -H "Content-Type: application/json" \
  -d '{"action":"set","sets":{...тот же объект целиком, с правкой...}}'
```

Обнуление молчаливо и не всегда заметно по симптомам сразу: `ReaderReadAHead`  
пролежал сбитым несколько часов и всплыл только как прерывания при просмотре  
4K-серии. Поэтому проверять надо не «стало ли нужное поле нужным», а **diff  
всего объекта до и после** — изменилось ли ровно то, что просили. Кламп при  
этом опознаётся тем же diff-ом: записанное значение не равно отправленному.

**Проверка результата — никогда не по ответу API** (он всегда возвращает то,  
что попросили, включая случайно обнулённые поля). Правильная проверка —  
двухступенчатая:

```
# Сразу: значение реально попало на диск, а не только в память процесса
MSYS_NO_PATHCONV=1 adb -s <ip>:5555 shell "su 0 strings /storage/emulated/0/Android/data/ru.yourok.torrserve/files/config.db" \
  | grep -oE '"ИмяПоля":[^,}]*'

# Обязательно: значение переживает реальный перезапуск процесса, а не только
# мгновенную запись (движок перезапускается САМ очень часто — 1316 раз в истории
# лога на этом устройстве, поэтому "сохранилось прямо сейчас" ничего не значит)
adb shell "su 0 am force-stop ru.yourok.torrserve"
adb shell "su 0 am start -a android.intent.action.VIEW -d 'magnet:?xt=urn:btih:dd8255ecdc7ca55fb0bbf813693f757df6f3e0c9&dn=Big+Buck+Bunny' -n ru.yourok.torrserve/.MainActivity"
# ...затем снова action:get ЧЕРЕЗ forward, и сверка в логе строки вида
# "Set listen port 42100" (а не "random autoselect (0)")
```

Диагностический торрент (тестовый магнит) убирать после проверки:  
`{"action":"rem","hash":"dd8255ecdc7ca55fb0bbf813693f757df6f3e0c9"}` <!-- pragma: allowlist secret --> через   
`/torrents`, не через `/settings`.

Один параметр за раз, снапшот `before/`+`after/` по общей конвенции — см.  
[snapshots-convention.md](snapshots-convention.md). Значение `TorznabUrls`  
и прочих полей, которых нет в таблице выше, не трогать — это дефолты,  
за них никто не отвечал экспериментом.

## UPnP / доступность порта извне — открытый вопрос

Пользователь регулярно сталкивается с нехваткой пиров/сидов именно на  
редких, малосидовых раздачах. Механизм: в таких раздачах велика доля пиров,  
которые сами сидят за NAT — они видят только тех, кто входяще достижим сам  
(есть проброшенный порт). DHT/PeX и публичный IP работают независимо от  
проброса — это не про обнаружение пиров, а про то, что часть уже найденных  
пиров не может _установить_ с нами соединение, если мы сами недостижимы.

Статус на 2026-08-30 — **проверено по факту, решено порт не пробрасывать**:

*   `PeersListenPort` зафиксирован на **42100** (было `0`/случайный) — без этого  
    никакой проброс не может пережить рестарт движка в принципе (движок  
    перезапускается сам очень часто).
*   Внешняя проверка [canyouseeme.org](https://canyouseeme.org) на порт `42100`:  
    **Connection timed out** — порт снаружи не отвечает, несмотря на  
    `DisableUPNP:false`. За всю трёхлетнюю историю `torrserver.log` нет ни одной  
    строки о реальной активности протокола UPnP (только повторяющиеся дампы  
    `Client config:`) — похоже, либо UPnP выключен/не поддерживается роутером,  
    либо эта сборка TorrServer его фактически не делает.
*   CGNAT исключён: `PublicIp4` из `torrserver.log` (`93.109.126.138`) совпадает  
    с внешним IP браузера пользователя — белый IP есть, проблема упирается  
    именно в роутер, а не в провайдера на уровне сети.
*   DHCP-резервация для Ugoos AM6 на роутере (`10:2C:6B:C5:2B:79 → 192.168.10.5`)  
    сделана — нужна независимо от решения по порту, чтобы IP приставки не уезжал.
*   Точечный ручной port forwarding **недоступен**: в клиентском аккаунте  
    роутера (Huawei OptiXstar, провайдер CYTA) форма «User-defined» в разделе  
    Port Mapping не имеет поля для номера порта — только выбор из  
    предустановленных сервисов (DNS/FTP/HTTP и т.п.). Это ограничение прошивки  
    на стороне провайдера, не имеющее отношения к TorrServer.
*   Единственный доступный в этом аккаунте механизм — **DMZ** (полный проброс  
    всех портов приставки). Проверено, чем это обернётся: помимо порта 42100  
    наружу попадут **Samba (139/445, `security=SHARE`, `guest ok=yes` — без  
    какой-либо авторизации)**, **JacRed (9117, без авторизации)**, **TorrServer  
    API (8090, без авторизации)** и Android TV remote-service (6466/6467); adb  
    (5555) защищён RSA-ключом, но тоже становится видимым сканерам. Решение —  
    **не включать DMZ**: риск (открытый Samba без пароля наружу) несоразмерен  
    выгоде (пиры на редких раздачах).

**Итог: порт не пробрасывается.** Если нехватка пиров станет критичной —  
следующий шаг не техническая настройка, а обращение в поддержку CYTA с  
просьбой либо добавить точечный NAT-проброс (42100/TCP+UDP → 192.168.10.5) на  
своей стороне, либо перевести устройство в bridge-режим (тогда роутинг/NAT  
переходит на отдельный собственный роутер без этих ограничений). До этого  
раздачи полагаются на DHT/PEX и на то, что хотя бы один пир в рое достижим  
напрямую — обычно этого достаточно везде, кроме самых редких раздач.

## Что уже компенсирует отсутствие входящего порта

Бэкенд TorrServer — библиотека `anacrolix/torrent`, у неё есть встроенный  
**holepunching (BEP 55)**: два пира за NAT могут установить прямое соединение  
через пира-релея, к которому оба уже подключены, без единого проброшенного  
порта на любой стороне. Это часть протокола, а не тумблер в настройках —  
условие только одно: не выключены DHT/PEX/uTP (`Disable*: false`, см. таблицу  
выше — уже так). Специально включать нечего.

`RetrackersMode:1` (см. таблицу выше) — отдельный от holepunching рычаг:  
подмешивает встроенный список публичных трекеров к раздачам, у которых своих  
трекеров мало или нет вовсе (проверено на диагностическом магните без единого  
трекера в самой ссылке — см. `snapshots/2026-08-30_torrserver-retrackers-mode/NOTES.md`).  
Работает через объявление трекеру, а не через входящую достижимость — полезно  
именно на малосидовых раздачах, независимо от решения не пробрасывать порт.

`EnableIPv6:false` и `EnableLPD:false` — не тронуты: IPv6 потенциально снял бы  
проблему NAT совсем (IPv6-адреса обычно без NAT), но не проверено, даёт ли CYTA  
нативный IPv6 на WAN; LPD помогает только пирам в той же локальной сети и для  
одного STB в квартире не даёт эффекта. Оба — кандидаты на будущее, не решения  
на сейчас.
