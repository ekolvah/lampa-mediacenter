# Снапшоты — конвенция бэкапа перед правкой конфигов на устройстве

Цель: перед любым изменением конфигурации на Ugoos AM6 (или другом устройстве
проекта) снять снапшот текущего состояния, только потом менять. Если что-то
сломалось — откат = `adb push` снапшота `before/` обратно.

**Каталог `snapshots/` в git не попадает** — он в `.gitignore` и остаётся только
на диске. Причина в разделе «Секреты» ниже. Из этого следует: журналом изменений
служит `NOTES.md` внутри самого снапшота, а не `git log`, поэтому NOTES.md
обязателен и пишется до изменения, а не после.

## Структура одного снапшота

```
snapshots/<YYYY-MM-DD>_<короткое-описание>/
  NOTES.md        — что меняем, зачем, каким именно шагом, как проверить результат
  before/         — файлы с устройства ДО изменения (тот же относительный путь)
  after/          — файлы с устройства ПОСЛЕ изменения (создаётся только когда
                    изменение подтверждено рабочим)
```

## Процесс (одно изменение за раз)

1. Написать `NOTES.md`: что меняем, зачем, как проверим, как откатим.
2. Снять `before/`:
   ```bash
   MSYS_NO_PATHCONV=1 adb -s <ip>:5555 pull "<путь-на-устройстве>" \
     "snapshots/<дата>_<описание>/before/<то-же-имя>"
   ```
3. Внести ровно одно изменение.
4. Проверить, что всё работает (воспроизведение фильма и т.п.) — не переходить
   к следующему изменению, пока это не подтверждено.
5. Снять `after/` тем же способом и дописать в `NOTES.md` фактический результат.

Машинной проверки «снапшот снят до изменения» пока нет — она заведена задачей
[#9](https://github.com/ekolvah/lampa-mediacenter/issues/9). Гейт `snapshots`
в [scripts/ci_check.py](../scripts/ci_check.py) проверяет только структуру уже
существующих каталогов: имя вида `<дата>_<описание>`, наличие `NOTES.md` и `before/`.

## Откат

```bash
# приложение, чьи данные восстанавливаем, должно быть остановлено
MSYS_NO_PATHCONV=1 adb -s <ip>:5555 shell "am force-stop <package>"
MSYS_NO_PATHCONV=1 adb -s <ip>:5555 push "snapshots/<дата>_<описание>/before/<файл>" "<путь-на-устройстве>"
MSYS_NO_PATHCONV=1 adb -s <ip>:5555 shell "am start <package>/<activity>"
```

`adb push` под root кладёт файл владельцем `root` и с чужим SELinux-контекстом —
приложение теряет доступ к собственным настройкам. Для данных приложения после
push обязательны `chown` на исходного владельца и `restorecon`, с проверкой `ls -lZ`.

## Важный нюанс: облачная синхронизация Lampa

Часть настроек Lampa (LocalStorage происхождения `http://lampa.mx`) синхронизируется
в облако через привязанный CUB-аккаунт (см.
[lampa-config-review.md](lampa-config-review.md)). Если изменение делалось через UI
приложения (а не прямой правкой файла), оно могло уже уйти на сервер — тогда просто
восстановить локальный файл недостаточно: при следующем запуске приложение может
засинкать состояние обратно с сервера и откат «потеряется». Для таких настроек
откатывать нужно тоже через UI/аккаунт, а не только push-ем файлов. Настройки,
которые правятся напрямую в файлах устройства и не завязаны на аккаунт (sysfs,
`persist.*` свойства, конфиги TorrServe), откатываются push-ем без оговорок.

## ⚠️ Секреты в снапшотах

Файлы Lampa (`settings.xml`, LocalStorage) содержат токен привязки аккаунта и
логин/пароль TorrServer, а скриншоты — что угодно с экрана. Репозиторий публичный,
поэтому весь каталог `snapshots/` выведен из git через `.gitignore`, и это
единственная причина, по которой снапшоты не версионируются.

Запрет машинный в трёх местах, см. [quality-gates.md](quality-gates.md):
`.gitignore` не пускает файлы в индекс, гейт `remote` краснеет, если под
`snapshots/` вдруг оказался отслеживаемый файл, а GitHub push protection стоит
последним рубежом на стороне сервера.

Если снапшот нужно кому-то показать — чистить руками и класть отдельно, а не
снимать игнор.
